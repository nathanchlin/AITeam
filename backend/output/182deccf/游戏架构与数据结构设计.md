### 1. 游戏逻辑架构：状态机设计

游戏的核心是状态流转。基于昆特牌的规则，我们需要一个严格的有限状态机（FSM）来管理进程。

#### **GwentGameState (游戏状态机)**

| 状态阶段 | 状态名称 | 逻辑描述 | 数据变更 |
| :--- | :--- | :--- | :--- |
| **1. 初始化** | `GAME_START` | 加载资源，初始化双方玩家数据。 | 重置 `PlayerStats`，加载 `Deck`。 |
| **2. 调度** | `MULLIGAN` | 玩家替换起始手牌中不想要的卡牌（通常限定次数，如2-3次）。 | `Hand` 卡牌移出 -> `Deck` 洗牌 -> 新 `Hand` 卡牌入队。 |
| **3. 部署** | `ROUND_PLAY` | **核心阶段**。红蓝方交替打出卡牌。如果一方选择“放弃”，则该方锁定。 | `Hand` -> `Battlefield`，计算 `TotalPower`。 |
| **4. 回合结算** | `ROUND_END` | 双方都放弃或手牌打完。比较战力，判定胜负。 | 更新 `RoundWins`，清空 `Battlefield` (除特殊卡外)，将卡牌移入 `Graveyard`。 |
| **5. 终局** | `GAME_OVER` | 任一方赢得 2 个回合。 | 记录战绩，销毁会话。 |

### 2. 核心数据模型

我们需要定义卡牌的元数据结构。为了支持复杂的特效和平衡性分析，必须将属性颗粒度细化。

#### **2.1 卡牌数据模型**

这是单张卡牌的原子结构，用于存储在数据库或JSON文件中。

*   **基础属性**：ID、名称、阵营、颜色（金/银/铜）、类型。
*   **数值**：战力（Strength/Power）。
*   **扩展属性**：护甲、忠诚度。
*   **能力系统**：由于技能复杂，建议使用“触发器-效果”模式。

#### **2.2 玩家状态结构**

*   **资源**：手牌数、卡组剩余数、胜负场数。
*   **状态标记**：是否已放弃、是否拥有先手权。

#### **2.3 战场区域**

战场分为双方各 3 个区域，外加中立区域。

*   ** Melee (近战)**: `Row_Type: 0`
*   ** Ranged (远程)**: `Row_Type: 1`
*   ** Siege (攻城)**: `Row_Type: 2`
*   **特殊区域**: 天气卡、领土加成卡。

### 3. JSON 数据结构设计

以下是为开发人员准备的 JSON Schema 参考，支持多阵营配置。

#### **3.1 单张卡牌定义**

```json
{
  "card_id": "nr_keira_metz_001",
  "name": "凯拉·梅兹",
  "faction": "NORTHERN_REALMS",  // 阵营：北方领域
  "color": "GOLD",               // 稀有度：金
  "type": "UNIT",                // 类型：单位 (特殊卡为 SPECIAL)
  "base_power": 5,               // 基础战力
  "provisions": 10,              // 卡组构建资源 (用于卡组平衡)
  "loyalty": "LOYAL",            // 忠诚度
  "row_restrictions": ["RANGED"], // 限制只能放在远程排
  "keywords": ["MAGE", "SPELL"], // 标签，用于检索
  "abilities": [
    {
      "trigger": "ON_DEPLOY",    // 触发时机：部署时
      "effect_type": "DAMAGE",   // 效果类型：伤害
      "target_scope": "ENEMY",   // 目标范围：敌方
      "value": 5,
      "description_key": "ability_keira_desc"
    }
  ]
}
```

### 4. 数据分析与平衡性建议

作为分析师，基于上述结构，我提出以下可视化与调整建议：

#### **4.1 平衡性监控指标**
*   **平均胜率**: 按阵营统计。
*   **使用率**: 统计每张卡在卡组中的出现频率。
*   **平均每回合战力产出**: 分析哪些卡牌过强，导致数值膨胀。

#### **4.2 可视化建议**
1.  **热力图**: 展示不同阵营在不同排的战力分布。
2.  **桑基图**: 展示一张卡从手牌 -> 战场 -> 墓地的流动过程。
3.  **雷达图**: 比较不同阵营的“爆发力”、“控制力”、“续航力”维度。

这个架构设计既满足了开发所需的严格定义，也为后续的数据分析（如卡牌平衡性调整）预留了足够的数据字段。如果您需要具体的 SQL 建表语句或更深层的算法逻辑，请告诉我。
